# Render deployment and live-service updates

Operator runbook for deploying Duesdesk to Render and pushing updates to the
running service. For database roles, backups and the go-live acceptance
criteria, see **DEPLOYMENT.md**; this file covers the Render mechanics and the
update path.

## No credentials are stored in this repository

There is no Render API key, no service ID, and no `render` CLI in this
checkout. Nothing here can read or change the live service; every change below
is a manual dashboard step for an operator with access. If you want the
deployments automated later, create a Render API key and store it in a password
manager or CI secret — **not** in this repository.

## What Render runs

From `render.yaml`, the blueprint is authoritative:

| Setting | Value |
| --- | --- |
| `runtime` | `python` |
| `buildCommand` | pip install lock, pnpm install/build, `findstatic`, `collectstatic`, `verify_static` |
| `preDeployCommand` | `migrate --noinput` then `deployment_check` |
| `startCommand` | `cd backend && python serve.py` |
| `healthCheckPath` | `/health/` |

A deploy therefore runs the build, then the pre-deploy step, then the server.
The app is only handed traffic once `/health/` answers, so a build or migration
failure is a failed deploy rather than a half-live service.

`verify_static` in the build deliberately runs as `APP_ENV=production`, because
only that storage backend writes the `staticfiles.json` manifest it reads back.
A build that collects static files under the local backend would pass without
proving the hashed manifest was built.

If you choose `runtime: docker` by hand instead, the blueprint is ignored and
you own every step it would have run. The image's `CMD` is `python serve.py`
and **does not migrate**, so add an explicit release command
(`python manage.py migrate --noinput && python manage.py deployment_check`)
or the app will start against a stale schema.

## Environment variables

The blueprint declares fifteen. Which are secrets is decided in
`render.yaml`; `generateValue: true` means Render creates the value, and
`sync: false` means Render prompts you for it when the blueprint is applied.

| Variable | Secret | Required | Notes |
| --- | --- | --- | --- |
| `APP_ENV` | no | yes | must be exactly `production` |
| `DJANGO_SECRET_KEY` | auto | yes | generated by Render; ≥ 50 characters |
| `DATABASE_URL` | prompt | yes | Neon **pooled** string for the running app |
| `ALLOWED_HOSTS` | no | yes | the hostname you actually serve; `*` is refused |
| `CSRF_TRUSTED_ORIGINS` | no | yes¹ | `https://` origins, comma separated |
| `TRUST_PROXY` | no | yes | `1` behind Render |
| `TRUSTED_PROXY_IP` | no | yes | see the proxy warning below |
| `TRUSTED_PROXY_HEADERS` | no | yes | `x-forwarded-proto` only |
| `BIND_HOST` / `PORT` | no | yes | `0.0.0.0` / `8000` |
| `PYTHON_VERSION` | no | yes | pinned by the blueprint |
| `EMAIL_HOST` / `_USER` / `_PASSWORD` | prompt | yes² | SMTP |
| `DEFAULT_FROM_EMAIL` | prompt | yes² | from address |
| `EMAIL_PORT` / `EMAIL_USE_TLS` | no | no³ | not in the blueprint |
| `GOOGLE_CLIENT_ID` / `_SECRET` | no | no⁴ | optional; see **GOOGLE-AUTH.md** |

¹ Satisfied automatically by Render's `RENDER_EXTERNAL_HOSTNAME`, which is
always set for a web service. Set it explicitly anyway if you add a custom
domain, or the redirect to that domain will be rejected as a cross-origin POST.

² Required for real password recovery. Configured settings do not prove
delivery works; test an actual reset email.

³ `settings.py` defaults these to port `587` and TLS on, which matches what
**DEPLOYMENT.md** documents, so the blueprint is not broken by omitting them.
It does mean the effective values are implicit: if your provider needs a
different port, or implicit TLS on port 465, set them on the service. Note
that `deployment_check` only verifies that `EMAIL_HOST` is set and
`DEFAULT_FROM_EMAIL` is not localhost — it does not test the port or a
handshake, so a wrong port passes the deploy gate and only fails on the first
real email.

⁴ Not declared in the blueprint as committed, so set them directly on the
service, or add them to `render.yaml` if you would rather the Blueprint prompt
for them. Google sign-in is optional and fails closed, so leaving both unset
is a valid configuration: the Google URLs refuse with an explanation and the
emailed code still works.

### The proxy warning

`TRUSTED_PROXY_IP=*` is only safe because Render's ingress strips inbound
forwarded headers. `TRUSTED_PROXY_HEADERS` must **not** include
`x-forwarded-for`: Render appends to that header rather than replacing it, so
its first value is whatever the client sent, and trusting it would let any
request choose the address recorded in the audit trail. `deployment_check`
refuses that combination, so the pre-deploy gate fails rather than shipping it.

## First deploy from the blueprint

1. Create the Neon project, and take the **pooled** connection string for the
   running app. Keep the direct string for migrations and checks.
2. In Render, choose **New → Blueprint**, point it at this repository, and pick
   `render.yaml`. Render creates the service and prompts for each `sync: false`
   secret.
3. Fill in the prompted secrets. `DJANGO_SECRET_KEY` is generated for you.
4. Set `ALLOWED_HOSTS` and `CSRF_TRUSTED_ORIGINS` to the hostname you will
   serve. If you change them later, see the update path below.
5. Attach the Neon database, then run the schema migration once and create the
   first organisation. `/signup/` is the intended route for the first
   secretary; `createsuperuser` alone grants no tenant access.
6. Run `python manage.py deployment_check` and work through the acceptance
   checklist in **DEPLOYMENT.md**.

## Updating the live service

### Before you start

`makemigrations --check --dry-run` must report no changes. A model change
without a committed migration fails the build, and a migration that has not
been rehearsed against a restore is a rollback you cannot undo.

### Routine code update

Push to the branch Render builds. With auto-deploy on, that is the whole
procedure:

```text
git push origin <branch-render-builds>
```

Then read the deploy log. In order you should see the build command, then
`migrate --noinput`, then `deployment_check`, then the server starting and
`/health/` passing. If auto-deploy is off, trigger it manually:
**Dashboard → service → Deploy → Deploy latest commit**.

### Confirming what actually shipped

The deploy log names the commit. Compare it with `git rev-parse HEAD` on the
branch you intended to ship. This is the only reliable way to know the service
runs your code; the running version is not visible from outside.

### Changing an environment variable

Environment changes do not take effect until a new deploy starts, so add the
variable and then redeploy. Two cases matter for this service:

- Adding a variable to `render.yaml` does **not** by itself reach a service
  that already exists. If the service was created from the blueprint, check
  whether the dashboard shows it as blueprint-managed and offers a sync;
  otherwise set the value directly on the service. A `sync: false` variable
  added later is a prompt, not an automatic value.
- Removing a variable from `render.yaml` likewise does not unset it on the live
  service. Delete it there too, or it will survive the next deploy.

### Verify after every deploy

```text
https://duesdesk.onrender.com/health/     -> 200 {"status": "ok"}
https://duesdesk.onrender.com/           -> 302 to /login/
```

Then sign in and confirm one real read and one real write, and check that the
audit history recorded the write with its request id.

### Rolling back

Render keeps previous deploys and can redeploy one. **Rolling back the code
does not roll back the database.** If the deploy you are reversing ran a
migration, the old code is now running against a newer schema. Before rolling
back a deploy that migrated, restore Neon to a pre-migration point or deploy a
forward fix; do not assume the rollback is sufficient.

## Troubleshooting

| Symptom | Cause | Fix |
| --- | --- | --- |
| `ImproperlyConfigured: ALLOWED_HOSTS is required in production` | variable missing or empty on the service | set it to the served hostname; `*` is refused |
| `ImproperlyConfigured: CSRF_TRUSTED_ORIGINS is required in production` | no origin and no `RENDER_EXTERNAL_HOSTNAME` | set the origin, or confirm the service is a web service |
| `APP_ENV must be exactly one of ...` | typo, or a value other than `local`/`test`/`production` | set exactly `production` |
| Build fails in `verify_static` | manifest missing because the build did not run as production | the build step must set `APP_ENV=production` and the hosts above |
| Every form POST returns 403 | origin missing for the domain you are on | add that domain to `CSRF_TRUSTED_ORIGINS` and redeploy |
| `deployment_check` refuses proxy headers | wildcard proxy trusted with `x-forwarded-for` | remove `x-forwarded-for` from `TRUSTED_PROXY_HEADERS` |
| Service starts, app 500s on real pages | migrations never ran | see the pre-deploy note below |
| Password reset never arrives | SMTP not configured or not verified | test an actual delivery, and verify SPF/DKIM |

### Confirm migrations are actually running

Render documents pre-deploy commands as a feature of paid plans. If your
service is on a plan that does not run `preDeployCommand`, the deploy will look
successful while never applying migrations, and the app will start against a
stale schema. Two ways to check, both worth doing on the live service:

- Read a deploy log and look for the `migrate` output between the build and the
  server start.
- Compare the schema to the models: run `migrate --plan` from a shell with the
  direct (non-pooled) connection string and see whether anything is unapplied.

If pre-deploy commands do not run on your plan, move the migration into a
one-off Render job or run it from an operator shell before each deploy.
